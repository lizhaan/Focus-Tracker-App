# Звіт-ретроспектива до лабораторної роботи №3

## Про проєкт

Focus Tracker — десктоп-застосунок, який через веб-камеру відстежує, чи зосереджений користувач на роботі. Ключова зовнішня бібліотека, якій присвячено цю ретроспективу, — MediaPipe 0.10.35, а саме FaceLandmarker із Tasks API.

Обробка кожного кадру проходить такий шлях: камера (OpenCV) → 478 точок обличчя та райдужок (MediaPipe) → відкритість очей, поза голови, положення райдужок → згладжування → регресія точки погляду на екрані → машина станів фокусу. Усе працює локально, кадри ніде не зберігаються.

## Які задачі мала вирішувати бібліотека

MediaPipe відповідає за ту частину проєкту, яку неможливо якісно реалізувати самостійно, — знаходження обличчя та його ключових точок на кожному кадрі. Конкретно бібліотека мала:

- визначати, чи є обличчя в кадрі (стани «обличчя не видно» та «відсутність за комп’ютером»);
- повертати 478 точок обличчя, зокрема контури повік і центри райдужок;
- давати дані, з яких рахуються відкритість очей (EAR), поза голови (Yaw/Pitch/Roll через `solvePnP` в OpenCV) і положення райдужок для регресії погляду.

## Чому саме MediaPipe

MediaPipe — єдиний із розглянутих варіантів, який водночас дає точки райдужок, працює в реальному часі на звичайному процесорі, встановлюється через `pip` і не передає дані назовні.

| Альтернатива | Чому не обрано |
| --- | --- |
| dlib (68 точок) | Немає точок райдужок; на Windows часто потребує збирання через CMake і компілятор C++ |
| OpenCV (Haar, DNN-детектори) | Дає лише рамку обличчя або кілька точок, чого замало для оцінки погляду й пози голови |
| Хмарні API розпізнавання обличчя | Суперечать вимозі приватності й потребують інтернету |

## Документація

Офіційні посібники Google AI Edge для FaceLandmarker короткі й корисні: для кожного режиму роботи є приклад на Python та опис параметрів. Водночас були й незручності:

- документація не пояснює, що означає кожен індекс точки, тому індекси повік і райдужок (468–477) довелося шукати на схемі канонічної моделі обличчя в репозиторії на GitHub;
- довідка з API (класи, поля результату) дуже лаконічна, тож частину поведінки довелося з’ясовувати експериментально.

## Проблеми під час розробки

- **Хибні відволікання при повороті голови.** Якщо користувач повертає голову, але очима все ще дивиться в монітор, система може помилково вирішити, що він відволікся.
- **Точність залежить від умов.** Коли користувач сидить далеко від веб-камери або освітлення погане, точки визначаються менш точно, і обрахунки погіршуються.
- **Зміна відстані до монітора.** Якщо під час роботи користувач сильно наближається до екрана або відсувається, детекція стає менш надійною; у такому разі краще пройти калібрування заново.

Щоб окремі хибні спрацювання не призводили одразу до втрати фокусу, я реалізувала машину станів: відволікання фіксується лише тоді, коли воно триває довше за заданий час, а короткі збої детекції ігноруються.
